# 汇集量化影子验证

本仓库是独立的影子研究系统。它只读取两个源仓库的公开产物，不导入源仓库内部代码，也不向源仓库写入任何文件：

- `njedu2023-prog/a-top10`
- `njedu2023-prog/top10-decision` 的 Premium 与 Decision 页面数据

## 已冻结的业务规则

1. 按证券代码对三张页面实际展示的候选求严格交集；交集有几支就保留几支，绝不补票。
2. 三源的 `D / T / T+1` 必须完全一致，并通过逐年认证的上交所交易日历Bundle验证严格后继关系；任一源缺失、错期或目标年度未认证，当日 `INPUT_BLOCKED`，不回退旧榜单，也不按工作日猜测开市。
3. 对全部交集候选重新量化排序，不把三个相关来源的概率相乘。
4. 严格交集中的每一支候选都进入独立影子账本；固定第1、第2、第3名继续分别统计，不足三个名次时显示“无候选”，不顺延、不补位。
5. T日按目标日期严格匹配的未复权开盘价作为影子成交价；缺少合法开盘价时保持“开盘价待补”，不虚构成交。
6. T日收盘后验证 `T日涨跌幅 / 是否晋级`；收盘前保持“待验证”，行情证据不足保持“待补证”，绝不把未知写成“否”。内部仍以收盘涨停事实作为晋级依据，但页面不重复显示同义字段。
7. T+1在 `[11:00, 11:05)` 分成五个一分钟子单退出；无法成交的余额保留为延迟退出，不删除样本、不虚构价格。
8. 当前版本不连接券商、不发送订单，所有记录均为影子验证。

源表里不影响展示成员资格的辅助字段缺失只产生质量警告，不会把实际展示股票踢出交集。Premium 重复表头仅在逐行值可安全合并时容错并告警；冲突值仍会阻断输入。

## 正式排序引擎 V2

新信号使用 `formal_ranking_engine_v2`。引擎只消费冻结于D日及以前的白名单特征：1/3/5/10/20日收益、5/20日波动、下行波动、ATR、振幅、CVaR、最大回撤、成交额/成交量、三源名次共识与分歧、晋级阶段以及明确允许的上游预测字段。成交额与成交量保持不同量纲；任何实际结果、标签、T日观察值或D日之后行情都不能进入特征。

每支候选统一产生三组有效预测：

- 按开盘价成交后的费用后净收益均值及10/50/90分位；
- T+1退出延迟概率与预期延迟交易日；
- T日晋级概率（辅助展示，不直接替代收益目标）。

为兼容既有数据结构，`p_fill / expected_fill_ratio` 仍保留，但在“开盘价即成交价”口径下固定为 `1`，不再参与排序或门槛。

排序目标为：

```text
风险效用
= 净收益均值
− 尾部风险权重 × 预期短缺
− 延迟权重 × P(延迟) × 预期延迟日
− 不确定性权重 × 不确定性
```

策略门槛与影子执行相互独立：门槛可输出 `NO_TRADE`，但三表实际交集的全部候选仍进入账本。任何候选的市场特征不足时，当日整个候选组统一退回三源Borda共识排序并关闭正式门槛，避免同日混用两套排名口径。

在样本达到晋级门槛前，冠军模型为完全可审计的 `transparent_shadow_champion_v2`。学习型挑战者采用固定白名单、训练集内中位数填补和标准化，以及收益分布/延迟/晋级多任务预测头；成交头仅保留为固定100%的结构兼容头。只有通过按D日整组的前推验证、标签期清除、交易日隔离、126日锁箱、成本压力测试和人工确认后，才能写入模型注册表成为冠军。JSON模型制品会校验相对路径、SHA-256、特征版本、训练截止日和验证标志；任何异常都自动回退透明冠军。

每个新信号还在D日冻结一份 `shadow_order_spec_v1`：按冻结涨停限价、单票资金、整手和费用预留计算确定申报数量。T日取得未复权开盘价后，该冻结数量按开盘价全额计入影子成交；历史信号缺少订单规格时，按其已冻结的涨停限价恢复申报数量，并保留迁移诊断。

看板中的 `0` 只表示已最终确认的现金日（如零交集）；未完成交易的收益为 `null`，页面显示“待验证”。同月同时存在最终与未完成记录时，收益标记为“暂定”，曲线在未完成点断开。延迟退出完全平仓后，单票收益按 `actual_exit_date` 归属，不回填计划T+1。

全部候选组合按每支相同影子资金计算。只有同一信号日的全部候选均最终结算后，才生成该日组合净收益；只要仍有一支未完成，该日组合收益就是 `null`，不会用已完成子集制造暂定收益。全部候选历史累计收益和月度累计收益对已最终的日组合收益复利；存在未完成日期时明确标注暂定。若同组候选分日退出，组合归属日取最后一支完成退出的实际日期。

## 单票研究 V3（影子审计已接入）

自本版起，每个新冻结信号先将严格交集候选、排名、`shadow_order_spec_v1` 和影子账本原子落盘，再进入可选的 `single_stock_research_audit_v1` 后置阶段。成功时该对象内含 `single_stock_snapshot_v3`、候选分析摘要、冻结订单摘要和D日分钟状态代理；采集、归档或构建失败时也必须保存带原因和完整指纹的 `UNAVAILABLE` 信封，不得回滚或擦除已落盘名单。它只对集成后的新信号生效；历史信号保持空值，不事后回填或重算。

- 每支严格交集候选冻结一份 `single_stock_snapshot_v3`，保存D日可知的规则事实、行情来源、完整性状态和研究结果；整个审计信封另有SHA-256指纹，分钟证据指纹覆盖日期、时间、OHLC、量额、价位、来源、复权和时间语义。
- 硬门控只使用 `PASS / BLOCK / UNKNOWN`：`PASS` 表示证据完整且未触发阻断条件，`BLOCK` 表示已有明确的确定性风险，`UNKNOWN` 表示关键证据不足。未知不得写成通过或阻断。
- 点时证券主数据使用 `point_in_time_security_master_v1`：记录必须带有效期、`known_at/fetched_at`、修订号、来源地址与内容指纹，覆盖停牌、ST、退市整理、板块交易规则、涨跌幅限制和最小价位。文件路径由 `config.paths.security_master` 显式传入批次。随仓库提供的是合法空启动集；未装载权威记录时所有相关字段保持 `null/UNKNOWN`，绝不从代码、名称、板块或默认配置推断 `PASS`。空集缺失证据使用其真实 `generated_at`；晚于D日的启动集不能事后冒充D日证据。
- D日分钟状态代理只在取得完整的240个连续竞价一分钟区间、日期与复权口径全部合法时计算。首次/最后“封板”、开板、回封、封板时长和一字板均只是分钟收盘价或OHLC状态代理，不证明盘口真实封单、撤单或队列。分钟数据不完整时保持 `UNKNOWN`，不得把未知计数填成0。
- 分钟研究使用独立的3秒单次请求、最多5票并行，整批另有15秒可终止硬截止；超时、采集或归档失败只生成 `UNAVAILABLE` 警告，不改变已落盘名单。规范化D日分钟OHLCV以确定性gzip、内容寻址的 `.json.gz` 对象独立追加保存；对象SHA-256绑定解压后的规范JSON，研究快照只保存路径、对象SHA、分钟内容SHA、条数与供应商等轻量引用。同内容重试不复制240根行情，只有内容修订才新增对象。
- V3首阶段的所有字段均为 `shadow/audit-only`：不改变三表严格交集，不删除、补入或换入候选，不改写已冻结名次，不改变当前冠军排序和 `shadow_order_spec_v1`。

当前系统没有真实T日9:25集合竞价盘口、未匹配量、前方队列或券商成交回报的生产者。T日未复权开盘价仅是统一的影子入场基准，不证明9:25的真实可成交性、排队顺序或可成交数量。在可靠的L1/L2或券商证据生产者接入前，不得宣称真实9:25执行门控已生效。

交易日历生产入口为 `data/trading_calendar_bundle.json`。2026年度依据上交所正式通知标记为 `VERIFIED`；截至2026-08-09尚无可认证的2027年度休市通知，因此2027文件只是无日期猜测的 `UNVERIFIED_AWAITING_OFFICIAL_NOTICE` 元数据候选。任何2027生产运行都会失败关闭，直到官方通知被独立核验并显式晋级。

## 运行

```bash
python -m pip install -e .
python -m unittest discover -s tests -v
python -m three_table_quant.cli --config config/system.json
```

输出：

- `data/state.v1.json`：不可覆写的信号与影子交易状态
- `data/dashboard.v1.json`：静态页面唯一数据源
- `data/source_issues.v1.json`：源端问题，只报告、不修复
- `data/model_registry.v1.json`：冠军/挑战者、制品校验和与晋级样本状态
- `data/single_stock_minute_archive/`：按年/D日/证券代码组织的追加式分钟gzip证据，不塞入看板或状态大对象

`data/execution_truth.v1.json` 继续保留为券商/逐笔证据的独立审计输入，但不再决定影子账本入场价；影子入场统一采用T日未复权开盘价。

## 自动化与发布

GitHub Actions 先用版本化的上交所交易日历判断当天是否为A股交易日，再分两个北京时间批次运行：19:00的验证批次不读取三张候选表，只核验已冻结名单的T日收盘涨跌幅/是否晋级并结算已到期的T+1退出；21:30的输出批次读取当日三源并冻结新的D日名单。为降低 GitHub 单一 cron 延迟风险，验证在18:40/18:55/19:10冗余唤醒，输出在21:10/21:25/21:40冗余唤醒；早到任务在运行器内等到准点，同日成功批次由幂等门控拦截，`DEGRADED` 验证则允许后续唤醒重试。状态读写与 Pages 部署使用独立并发锁，Pages 排队或卡住不再阻塞下一个名单/验证批次，新 Pages 部署会取消过时的旧部署。休市日两个定时批次都会在交易日门禁处安全跳过，不请求行情、不读取三源，也不发布伪造的0支名单。若三源尚未同日就绪，21:30同一次任务每5分钟重新读取一次，最长等待120分钟；三源对齐后立即冻结新信号并再次幂等结算待处理状态，等待超时则发布最新 `INPUT_BLOCKED` 时间与原因而不伪造名单。两个交易日批次在发布前分别校验看板中的计划时间、实际运行时间、完成状态与候选数量，并要求实际完成时间不早于本次任务启动时间，旧页面不能冒充本次成功。19:00另按本批 `T_DAY / ENTRY / EXIT` 到期义务记录完成、待数据、延期和失败；没有到期义务也明确记录 `SUCCESS_NO_DUE`。程序层面另设20:00首次冻结硬门禁。读取时先固定两个源仓库各自的远端commit SHA，再从固定commit获取全部指针与日期文件。严格交集为0时仍冻结一条 `NO_CANDIDATE` 批次、更新时间并明确记录“名单筛选已执行、0支、合法空选”。GitHub Actions 定时为尽力按时，可能因平台排队延迟；看板保存计划时间与实际执行时间，不用计划时间冒充实际时间。源码或页面的路径受限 `push` 只运行全量测试并部署已提交页面，绝不运行名单/验证程序，也不写入运行数据；生成数据提交因此不会循环触发或在休市日伪造执行。
